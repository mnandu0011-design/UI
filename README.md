## Topic Research

### What is this UI pattern?

A service-management UI helps users request services, report incidents,
track tasks, monitor service status, and manage workflows from a
consistent workspace. Common patterns include dashboards, searchable
tables, status badges, filters, forms, detail panels, and clear action
buttons.

### Where is it commonly used?

These patterns are commonly used in IT service management (ITSM),
internal employee portals, help desks, incident management systems,
service catalogs, and workflow automation tools.

### Why is it relevant to modern web interfaces?

Organizations need interfaces that make complex processes easier to
understand and complete. Responsive layouts, clear status indicators,
accessible forms, searchable data, and reusable components help users
work efficiently across different screen sizes.

### Design and interaction patterns observed

-   Dashboard cards for key metrics and summaries.
-   Tables or lists for requests, incidents, and tasks.
-   Status labels to communicate progress and priority.
-   Search and filtering to find relevant records.
-   Forms with clear labels and validation feedback.
-   Navigation that groups related service-management areas.
-   Responsive layouts for desktop, tablet, and mobile screens.

### What this implementation aims to add

This collection aims to provide a clean, responsive, beginner-friendly
set of original templates using plain HTML, CSS, and JavaScript. The
components should be easy to understand, adapt, and reuse. Any
interactive behavior is implemented for demonstration and does not imply
a connection to a live ServiceNow instance.

## GitHub Collaboration Workflow

All team members should contribute through individual branches and Pull
Requests rather than committing every change directly to `main`.

1.  **Fork** the team repository (if working from an upstream
    repository).
2.  **Clone** your fork.
3.  **Create a branch** for your task.
4.  **Develop** the UI and test it in a browser.
5.  **Commit** with a clear message.
6.  **Push** the branch to GitHub.
7.  **Open a Pull Request (PR)** describing the changes.
8.  **Review** another team member's PR and provide constructive
    feedback.
9.  **Address feedback** and update the PR if needed.
10. **Merge** the approved PR according to the team's rules.

Example branch names:

-   `feature/service-dashboard`
-   `feature/service-catalog`
-   `feature/incident-list`
-   `fix/responsive-layout`
-   `docs/update-readme`

Example commit messages:

-   `feat: add service dashboard template`
-   `feat: create service request form`
-   `fix: improve mobile navigation`
-   `docs: update project README`

## Contribution Guidelines

-   Use meaningful file, class, branch, and commit names.
-   Keep HTML, CSS, and JavaScript readable and organized.
-   Make layouts responsive and test them in a modern browser.
-   Prefer reusable components and avoid unnecessary dependencies.
-   Build original designs; use references for research, not for
    copying.
-   Describe the purpose and screenshots of each new template in its PR.
-   Review teammates' code respectfully and test changes before
    approving.
-   Keep the README accurate as the project evolves.
